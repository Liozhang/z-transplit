# 兄弟仓库回授优化清单（2026-09-30）

> 背景：本仓库（z-transplit）与 z-search 均从 leadero 拆分而来。2026-09-30 完成了三仓的逐文件级交叉分析（能力清单、同源文件内容级差异、融合冲突面）。分析同时发现了**本仓库自身值得从两个兄弟仓库反向吸收的改进项**，记录于此。
>
> 完整分析主文档在 leadero 仓库：`D:/github_code/leadero/docs/zsearch-ztransplit-integration-analysis-2026-09-30.md`。本仓库的多项成果（十三个缺陷修复、提示词模板系统、持久翻译缓存、阅读模式双语对照、句子级朗读、原文真删除、真机探针质量保障等）已被该文档列为 leadero 的融合来源，此处不重复；下文只列**本仓库待办**。
>
> **实施状态（2026-09-30 当日落地）**：第 1、2、3（供应商内省部分）、4、5、6、8 项已全部实现并通过全量测试（394 个）、结构检查（9/9，无警告）与生产构建；第 3 项的流式空闲检测子项与第 7 项未实施，理由见各节末尾的「实施记录」。

## 一、优先级高：引擎韧性与用户可达性

### 1. Bing 网页端引擎升为可显式选择（从 z-search 搬）✅ 已实施

**证据**：z-search 于 2026-09-28 把 `bing-web` 从「Google 失败后的隐藏回退」升为可选引擎，注释记录了理由：它是大陆唯一无密钥可达的翻译引擎，必须让用户能**预先选择**——否则每段翻译都要先付出约 10 秒的 Google 端点超时才轮到回退。

**本仓库现状**：引擎列表为 Google / Bing（Azure）/ DeepL / AI / 自定义 / zotero-pdf-translate 六项，Bing 网页端只作为 Google 的失败回退存在。大陆用户无可预选的免密钥引擎，每次翻译先付超时成本。

**处理**：对照 z-search 的 `src/core/translation/translationEngines.ts`（引擎类型联合加 `bing-web`、工厂新分支、设置面板选项）搬入。本仓库已有的 `toBingWebLang` 修复（`auto` 映射 `auto-detect`）与 z-search 的 `detectBingSourceLang`（按 Unicode 区段判定源语言）是互补解法，可一并参考：显式 `auto` 走映射，未传源语言走区段判定。工作量小。

**实施记录**：引擎类型联合加 `bing-web` 并新增工厂分支；`featureReadiness` 把它列为免配置即就绪；设置面板新增下拉项与说明区块；两语言 FTL 补齐。源语言按文档口径二分：显式传入（含显式 `auto`）走既有映射，未传源语言走新增的 `detectBingWebSourceLang` 区段判定。相关既有断言（回退链 `fromLang`）已随新行为更新。

### 2. 翻译引擎调用的限流退避（从 leadero 学）✅ 已实施

**证据**：leadero 的 `src/core/search/WebSearchProvider.ts` 有统一 429 退避包装（优先读重试间隔响应头；间隔过大直接终态不占超时预算；无头时 5 秒退避加抖动；限流专门文案）。

**本仓库现状**：DeepL 免费版（每月 50 万字符、并发受限）与 AI 端点的 429 以原始形态冒泡为翻译失败；批量全文翻译（数十段并发）恰好是最容易触发限流的调用模式。

**处理**：参照 leadero 的 `requestWithRateLimit` 思想给引擎层加轻量退避（至少 DeepL 与 AI 引擎路径）。工作量小到中。

**实施记录**：新增 `src/utils/rateLimit.ts`（Retry-After 解析、指数退避加抖动、终态判定，纯函数有单测）；HTTP 辅助与 `openaiCompat` 在错误上附着 `status` 与 `retryAfterSec`；DeepL、AI、自定义三个引擎的单段路径包一次退避重试（重试仍 429 以 `translation-error-rate-limited` 专门文案终态并保留 `cause`）；批处理重试环的固定 500 毫秒间隔改为限流感知（Retry-After 优先，超长直接落逐段兜底）。Google 路径不包装：其失败本就由 Bing 网页兜底吸收。

## 二、优先级中：架构增强

### 3. AI 路径的流式空闲检测与供应商内省（从 leadero 学）◐ 部分实施

**证据**：leadero 的 AI 翻译路径有两样本仓库没有的能力：

- **流式空闲检测**（`executeWithIdleTimeout`）：包装请求的输出流，每个输出事件重置空闲计时器——长批流式输出只要还在产出就不会被总超时误杀。本仓库因直连客户端非流式，退化为 5 分钟总超时：慢而持续产出的推理模型可能被总闸误杀，卡死不产出的反而要等满全闸。
- **供应商内省**：动态调用 `provider.getContextWindow()` / `getMaxOutputTokens()` 取上下文窗口与输出上限，替代固定常量（本仓库硬编码 128000 / 16384）。

**处理**：短期可先做供应商内省（配置端点元数据或按模型名查表）；流式支持需给 `src/core/ai/openaiCompat.ts` 加流式解析，工作量中。leadero 的实现可直接对照。

**实施记录**：新增 `src/core/ai/modelCatalog.ts` 按模型名查表取上下文窗口与输出上限（gpt-5 / gpt-4.1 / o 系列 / Claude / Gemini / DeepSeek / GLM / Qwen / Kimi 等家族，取值方向刻意保守，未识别模型沿用原常量），批量翻译的预算计算接入查表结果；有单测。**流式空闲检测未实施**：需给 `openaiCompat.ts` 加流式解析（SSE 逐事件），且真机验证成本高，留待后续单独一批。

### 4. 网络区域设置（从 z-search 搬）✅ 已实施

**证据**：z-search 的 `src/utils/region.ts`（242 行 + 42 个测试用例）：区域三态（自动 / 全球 / 中国大陆）、「只覆盖出厂默认」的推荐值机制（用户显式选过的引擎永不被区域选择推翻）、区域限定端点可镜像改指。

**本仓库现状**：完全没有区域概念。而**翻译引擎恰恰是区域差异最大的场景**——大陆用户 Google 端点不可达、免密钥引擎里只有 Bing 网页端可达；Azure 翻译的区域参数也因区域而异。当前用户的唯一办法是自己逐项试出可用引擎。

**处理**：搬 `region.ts` 机制，推荐值表按翻译场景定制（大陆 → Bing 网页端或 Azure 中国北部区域；全球 → Google）。工作量中。

**实施记录**：新增 `src/utils/region.ts`（区域三态、按翻译场景定制的推荐值表、「只覆盖出厂默认」守门逻辑，偏好读写注入可测）；`prefs.ts` 补齐写入与清除原语；`addon/prefs.js` 声明 `region` 键；设置面板翻译引擎组新增「网络区域」下拉（自动 / 全球 / 中国大陆），选定即套用推荐值并以本地化提示回显写入结果（面板脚本与 `region.ts` 的推荐值表互为镜像，注解要求保持一字不差）。z-search 的区域限定端点镜像与功能显隐两节不适用本仓库，未搬。

## 三、优先级低：质量保障与长期维护

### 5. 多语言死键守卫（从 z-search 学）✅ 已实施

**证据**：z-search 的 `tests/unit/i18n/no-dead-keys.test.ts`：多语言字典中每个键必须被代码引用，死键守卫。其清理历史很有说服力——从上游整体抄来 4541 键，其中 4099 个是死词，删至 442 活键；同时守护三语言键集与生成目录三方一致。

**本仓库现状**：结构检查第五项（FTL 键覆盖）验证的是「代码引用的键都有定义」这一方向，不查「定义的键都被引用」的反方向；也无生成目录对账。当前 278 键规模尚可控，随功能增长值得补。工作量小。

**实施记录**：新增 `tests/unit/i18n/no-dead-keys.test.ts`：全库死键扫描（含 `data-l10n-id` 引用，动态键家族白名单登记）与中英键集一致性两条用例。清理发现的历史死键 `pane-title`（两语言）。本仓库无生成目录，无此项对账。

### 6. 源码硬编码中文守卫（从 z-search 学）✅ 已实施

z-search 的 `no-hardcoded-cjk` 测试：源码不允许硬编码中文界面文案（否则英文界面向用户露出中文），用 TypeScript 词法扫描器而非正则实现（AI 提示模板里的块注释样例会让朴素的注释剥离大量误报），带按文件白名单（分词器样例等「是数据不是文案」的场合逐项登记理由）。本仓库已把历史硬编码中文提示迁移到多语言键（`getString`），但没有守卫防止回潮。工作量小。

**实施记录**：新增 `tests/unit/i18n/no-hardcoded-cjk.test.ts`（TS 扫描器，扫描 src 与 addon 的字符串字面量与模板串）。扫描即抓到一处真漏网：面板脚本里数据目录的回退文案，已改走 FTL 隐藏节点搬运（顺带修复英文界面露中文）；`modelCatalog` 的规则依据注记由字符串改为注释。白名单两项：`platform.ts`（macOS 字体文件路径数据）与 `splitViewFactory.ts`（Java 缺失与网络错误的跨平台签名匹配模式）。

### 7. MinerU 云端备援的重新评估（产品决策）⏸ 未实施

本仓库移植时刻意删除了 leadero 的 MinerU 远程后端（单后端是当时的设计决定）。leadero 侧的双后端级联（`parsePdfWithFallback`：基础设施错误自动切换并告知用户）提示一个值得重新评估的场景：**本机无 Java 且用户不愿下载运行时**时，云端解析是唯一的免 Java 路径；反之 Java 可用时 MinerU 自带公式结果还能省掉视觉模型的公式再提取。若重评估通过，leadero 的级联实现可直接对照。工作量中到大。

**实施记录**：产品决策，保持原设计（单后端），未改动；待产品侧重新评估后再立项。

### 8. 版本化偏好迁移机制（从 leadero 学）✅ 已实施

leadero 的 `src/utils/prefMigrations.ts`：按 `prefSchemaVersion` 版本号顺序执行迁移步骤的机制。本仓库当前 31 个键、偏好结构简单，尚无刚需；键数增长或语义变更（如批大小从字符量纲改 token 量纲这类两兄弟仓库都遇到过的场景）时值得先行引入。工作量小。

**实施记录**：新增 `src/utils/prefMigrations.ts`（有序步骤表、逐步落版本号、失败停步下次重试、整体不阻断启动）；`prefs.ts` 补充的写入与清除原语为其铺路；`addon/prefs.js` 声明 `prefSchemaVersion`（出厂 0）；`src/hooks.ts` 在 Zotero 初始化完成后调用。当前版本 1（基线标记），后续偏好结构变化从这里追加步骤。
